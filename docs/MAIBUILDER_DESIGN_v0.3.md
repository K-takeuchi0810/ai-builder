## 1. コンセプトと位置づけ

重視する項目(パラメータ)を選んで「マイAI」を組み立て、印(◎○▲△×)と
その根拠(寄与分解)を確認できる、**個人利用主体の予想分析ツール**。

### 位置づけ

- 主用途は作者自身の利用(当日の印確認・レース観戦の補助)。
- 10月にお客様へ「一エンジニアが作ったツール」として紹介する機会がある。
  紹介はライブデモ(マイAI作成→予想→ライブ更新)で行うが、専用の演出・
  進行要件は設けない。
- 本ツールは回収率商品ではない。F3-EDGE-001により、特徴量選択×線形重みの
  空間には単勝市場を上回るOOSエッジが存在しないことが確定している。
  的中率でも1番人気ベースラインに勝てない(実測: 約20% vs 33%)。
  この事実はツール内で隠さず、ベースライン併記により常に可視化する。

### 利用上の原則(作者自身への規律)

- 印・寄与分解は分析の可視化であり、賭け金の判断根拠にしない。
  納得感のある寄与分解は主観的確信を強めるが、エッジの不在とは独立である。
- **回収率は表示する (2026-07-27 の判断で変更)。ただし点推定を単独では出さない。**
  ブートストラップ信頼区間・最小レース数(50)・控除率上限(約80%)・最大配当の
  占有率を必ず併記し、区間が重なる相手は同順位にする。1日36レースでは回収率は
  「◎に30倍が来たか」でほぼ決まるため。実装は `builder/roi.py`、
  機械検査は `tests/test_web_ui.py::test_roi_is_never_shown_as_a_bare_point_estimate`。

### DO / DON'T

- DO: 事実ベースの成績(的中率・ベースライン差)を表示する。
- DO: 印の根拠(セル単位の寄与)を常に表示可能にする。
- DON'T: 「儲かる」を暗示する文言・演出を入れない(回収率の表示解禁は数値の話であって、
  煽り文言の解禁ではない。`test_no_profit_promising_vocabulary` で固定)。
- DON'T: 対抗戦・勝負・煽り系の語彙を使わない(「成績比較」「基準との差」で表現)。

## 2. スコアリング対象と市場人気の扱い(v0.3で確定)

### 参加者AI(マイAI)

- スコアリングに使うのは**参加者が選んだ項目のみ**。「人気(市場)」は
  選択肢に含めず、参加者AIのスコアにも一切混入させない。
- 根拠: 同時学習で人気を含めると重みが人気に集中し(全重みの23.8%)、
  ◎の95.9%が1番人気と一致、項目追加で◎が変わる割合0.2〜2.2%となり、
  「選んだ項目が根拠になる」という商品定義が崩れる(実測: 2026-07-26 FINDINGS)。

### 1番人気AI(ベースライン)

- 単勝人気順に印を打つAIを常設し、全成績表示に併記する。
- 市場の強さはベースラインとの差分として表現する。これはF3の結論
  (市場には勝てない)のツール内表現である。

## 5. スコアリング(v0.3で確定)

### プリセット重み: 列別(単独)学習

- 各列を単独の条件付きロジットで学習した係数を保持し、参加者の選択列の
  重みとして適用する。任意の部分集合で整合的(同時学習は全425列同時でのみ
  有効で、一部の単独選択では一様分布より悪化することを実測)。
- 既知のトレードオフ: 列別学習は項目間相関を無視するため、相関の強い項目を
  複数選ぶと同一情報が重複して効く。順位付けと寄与表示の用途では許容とする。
- 学習経路は normalize.py のカバレッジゲートを共有(train-serve一貫、
  ゲート通過レースのみが勾配に寄与。カレンダーでの学習窓管理はしない)。
- オプティマイザはバックトラッキング付き(発散の回帰テスト: lr=0.1/1.0/50.0)。
  採用条件: 学習後対数尤度 ≥ 一様分布。

### 欠損ポリシー(MISSING_DATA_POLICY.md)

- 列のカバレッジゲート: 値を持つ馬が4頭未満または半数未満なら、その列は
  レース内で不使用。
- 値が無い馬は寄与0(中立)。再正規化はしない(薄い実績の増幅を防ぐ)。
- カバレッジ(n_used / n_with_value)を常に返し、UIで開示する。

### 印と自信度

- スコア降順に◎○▲△×、6頭目以降は無印(全頭表示、無印は「なぜ無印か」の一文つき)。
- 自信度3段階(鉄板級/有力/混戦)は**尺度不変のスコア差**で判定
  (選択列数に依存しない。学習期間の分位点で閾値を事前決定し、列別重み確定後に最終固定)。
- 寄与表示は絶対値でなく**押し上げの割合(%)**で示す(列別重みは絶対値が小さく
  小数1桁では無意味なため)。

## 7. 本日の成績比較(旧リーダーボード)

- 複数のマイAIの当日成績(◎的中数・複勝率・出し抜き数)を並べて表示する。
  個人利用では自分のAIバージョン間の比較、紹介時は触った人ごとの比較に使える。
- 順位規則(確定): ①◎的中**率** → ②出し抜き数 → ③◎複勝率 → ④同点は同順位。規則を画面に明記。
  - 2026-07-27 修正: 第1キーを的中数から的中率へ。レースごとに適用AIを切り替えられる
    ようになり AI ごとに母数が異なるため、絶対数では母数の多いAIが機械的に上位になる。
- 1番人気AIは基準行として背景を変え、順位数字を付けない。
- ポイント制・対抗戦演出は不採用(v0.3で確定)。

## 7.6 回収率ランキング (2026-07-27 追加)

`GET /api/roi_ranking` が保存済みマイAI全部を **表示期間の全レース** で集計して並べる。

- **当日36レースでは集計しない。** 回収率の最小レース数は50で、1開催日では届かない。
  回収率は蓄積して初めて意味を持つので、1日単位で競わせない。
- 順位は **信頼区間が重なる相手を同順位** にする。全員が重なる場合は
  「順位は付けられません」と出す。
- 基準の1番人気AIは値を出すが順位は付けない (競う相手ではない)。
- 実測 (3,702レース): マイAI 68〜75%、**1番人気AI 77%**、区間はすべて重なる。
  控除率上限は約80%。回収率で市場を上回る設定は見つかっていない。

## 7.5 買い目・スマッピーQR (2026-07-31 更新)

印を券種ごとに並べ替えて表示する (`builder/betslip.py`)。単勝・複勝・馬連・
ワイド・馬単・三連複を、◎を軸にした素直な組み方で出す。

- **金額は参加者が買い目ごとに入力する。** 既定は1点100円、100円単位。
  ツールが回収率や印から賭け金を推奨・自動決定しない。
- レースを開いた直後は買い目を空にし、予想一覧を押し下げない。「印から買い目を作る」は
  任意操作として残す。
- 選択した各点には取得済みのオッズと概算払戻を表示する。値が無ければ推測しない。
  発走前画面へ `data_div=5` の確定オッズを混ぜない（PITゲート）。
- 予算からの資金配分は全点のオッズの逆数を使い、概算払戻を均等化する100円単位の配分とする。
  全点のオッズが揃わない場合は実行せず、範囲オッズは下限値を使う。
  印・スコア・期待値から配分比率を決めず、利益を保証する表現をしない。
- **QRの投票用データを独自生成しない。** 買い目と金額をJRA公式生成サイト
  (`qrcode.jra.go.jp`) へ送り、JRAが返したレコードが送信内容と完全一致した場合だけ、
  JRA生成データをQR画像にする。公式画面の変更や不一致時は停止する。
- QR作成は購入ではない。発売機でレース・式別・組番・金額・合計を確認して購入する。
- 「これは印の並べ替えであって推奨ではない」旨と、◎的中率の実測 (約20%、
  1番人気は約33%) を必ず併記する。

## 8. データ規律(PIT)

## 10. Claude Code 向け DO / DON'T(累積)

- DO: 参加者選択は基底列の線形結合のみで表現。スコア計算はすべてサーバ側。
- DO: すべてのスコアレスポンスに寄与分解とカバレッジを含める。
- DO: 全経路でPITゲート・欠損ポリシー(normalize.py)を共有する。
- DON'T: ユーザー設定ごとに compute_features を再実行しない。
- DON'T: 回収率を **点推定だけで** 出さない(信頼区間・レース数・控除率上限を必ず併記)。
- DON'T: スマッピー投票のデータを推測・独自生成しない。JRA公式サイトが返した
  データと、同サイトが受理した買い目の完全照合を必須にする。
- DON'T: 印・スコア・回収率から金額を推奨または自動決定しない。
- DON'T: 「人気(市場)」を参加者AIのスコア・選択肢・寄与に混入させない。
- DON'T: 探索的な重み最適化を追加しない(F3-EDGE-001で棄却済み)。
- DON'T: 学習窓をカレンダーで操作しない(ゲート方式で管理)。
- DON'T: フレームワーク・ビルドツール・Webフォント・外部CDNを導入しない。
- DON'T: フォント.72rem未満/タップ標的44px未満を新設しない。

| D-2 | `--ink-faint` (#8B9486) が白地 3.14:1 で AA 不適合 | `#66705C` (4.81:1) へ。文字用に `--gold-text` (#7A5D0F) を新設 |
| E-1 | オッズの再取得が馬体重発表のみ | `odds_as_of` の変化で再取得 + 「更新」ボタン |

### 再発防止に足したテスト

- `tests/test_dom_structure.py` — **作成画面も実描画**して検査する
  (A-2 を見逃したのは予想画面しか描画していなかったため)。
  button/input の入れ子、ⓘ の兄弟性、期間スライダーの本数、セル数表示の存在。
- `tests/test_web_ui.py` — パレットの WCAG コントラストを計算して固定
  (`--ink-faint` を旧値に戻すと3件落ちることを確認済み)。フォントサイズ下限も `.78rem` に。

### 実装上の判断

- **期間の複数選択は消さない。** スライダーは「直近N走」を1つに確定させるが、
  内部の `lookbacks` は Set のまま。複数持つ保存済み設定は**黙って書き換えず**、
  「期間を◯種類使っています。スライダーを動かすと1つにまとまります」と表示して保持する。
- **期間の ON/OFF は checkbox ではなく button チップ。** `<label>` で checkbox を包むと
  プログラム的な click が label に転送されて二重トグルになる事象が実機で出た。
  正本は `sel.step2` に置き、DOM の `checked` に依存しない (`aria-pressed` で状態を伝える)。

## 13. 買い目を参加者が組む (2026-07-29)

§7.5 の買い目は印の並べ替え固定だったが、参加者が自分で組めるようにした。
流れは公式サイトとマークカードと同じ「**券種 → 買い方 → 馬(枠)**」で、
作った買い目は**リストに追加していく** (1レースで複数券種を買うのが普通)。

### 券種は8種すべて

単勝・複勝・枠連・馬連・ワイド・馬単・三連複・三連単。
買い方は ながし(着固定を含む) / ボックス / フォーメーション。

- **フォーメーションの段数は券種の `size` が決める** (2頭系は2段、3頭系は3段)。
  段の見出しは順序ありなら「1着候補」、順序なしなら「1頭目」
- **枠連は枠で選ぶ。** 同じ枠に2頭以上いる枠は**ゾロ目** (`8-8`) も作る。
  1頭しかいない枠のゾロ目は作らない (成立しない)
- 印が付いていない馬も選べる。印は相対順位の可視化であって推奨ではないと
  明記しているので、印の馬だけに制限すると印を権威として扱うことになる
- **どの券種・どの買い方が有利かは示さない。** 実測でエッジが無いので示せる
  根拠がない。点数だけを出す
- 金額は買い目ごとに100円単位で参加者が入力する。印やスコアからは決めない

### 出力は「1点ずつの一覧」

買い方は**点を作るための道具**でしかなく、出てくるのは個々の組。だから公式サイトで
「通常」として1点ずつ入れても同じものが買える。方式が公式の選択肢と一致していなくても、
買えない買い目にはならない。

### 不変条件

1. **表記・点数・入力欄の段数の正本はサーバ。** UI は `/api/features` の券種仕様と
   `/api/betslip` の結果を出すだけで、`combos` を読まない。馬単の「11→10」を UI 側で
   組み立て直して方向を落とした事故があり、それは公式サイトへ渡す経路そのもの
   だった。数え間違いも段数の不一致も同じ経路なので、すべてサーバに寄せた
   (テスト: UI に `permutations` / `combinations` / `.combos` が現れないこと)
2. **順序なしの券種は組の中も番号順。** 公式サイトの入力は番号順のマス目なので、
   「11-3」のように軸を先に出すと転記でずれる。順序ありは並べ替えない
3. **出走していない馬番・そのレースに無い枠は組まない。**
4. **1件の指定違いで全体を止めない。** `skipped` に位置・理由・直し方を入れて他は作る
5. **フォーメーションの重複は1点にまとめる。** 順序なしの券種では段をまたいで同じ組が
   でき、点数が二重に数えられるとQRの点数と合わなくなる
6. **何を選んだのかを段ごとに見せる (`picks`)。** 点の一覧だけだと、フォーメーションで
   「1着候補に誰を入れたか」が追えない (`11→3→2` と `11→10→6` が並んでいても
   2着候補が読み取れない)。見出しと番号の並べ方もサーバが決める。
   点の内訳は畳んでおくが **消さない** — QR読取り後の照合に必要
7. **JRA送信は全件成功か全件停止。** `skipped` が1件でもあればQRを作らず、
   JRA応答の買い目が送信内容と完全一致しない場合もQRを表示しない

### 併せて直したもの

- `do_POST` の未処理例外が接続を黙って切っていた (実際に `/api/betslip` の
  `NameError` でそうなった)。UI からは「サーバが落ちている」と区別できないので、
  500 と理由を返してログに残す
- 壊れた形の `selection` (旧形式の dict など) で例外を投げず 400 を返す
- 入力欄の見出しを `name.startswith("p")` で判定していたため、`partner` と `pick` が
  巻き込まれて見出しが英字のまま出ていた。キーの集合で判定するよう修正し、
  **全券種・全買い方の見出しが英字でないことをテストで固定**

### CSS の重複定義について

一括編集で範囲の始点と終点を逆に取り、CSS 150 行ほどを複製した。後方の
`.bs-k{width:5.2em}` が前方の `.bs-k{font-weight:700}` を黙って上書きし、
**エラーは出ないが画面が崩れる**状態になった。

- 範囲を取る編集は「開始 < 終了」を確認してから使う
- `tests/test_web_ui.py` に **同じセレクタを2回定義していないこと** を検査するテストを追加
- 併せて、どこからも使われていないクラスを検出するテストも追加
  (`w1`〜`w8` のように JS が `w${waku}` で組み立てる名前は除外を明示する)

## 14. 選び直しによる楽観バイアスへの歯止め (2026-09-17)

### 問題

表示期間 (20250701〜) はプリセット重みの学習に使っていないので、**重みから見れば**
out-of-sample。しかし **参加者の項目選び** から見ればそうではない。良い数字が出るまで
選び直せば、その数字は選び直した回数のぶんだけ楽観側に寄る。
182,594 候補を機械で探索して out-of-sample のエッジが出なかったのと同じことが、
手作業でも起きる (`evidence/20260726_FINDINGS_preset_weights.md`)。

### 入れたもの

**① 世代カウンタ。** `configs.py` の `versions[]` に世代履歴はあったが画面に出ていなかった。
世代ごとの調整側スコアを `entry["scores"]` に記録し、2世代目から並べる。
**「選ぶほど上がっていく」形そのものが過学習の痕跡**になる。

**② 封印期間。** `DISPLAY_HOLDOUT_FROM` (既定 20260401) 以降を調整側の集計から外す。
実測で 表示期間 3,702 レースを 調整側 2,586 / 封印側 1,116 に分ける。
両側とも `MIN_RACES_FOR_RATE` (100) を大きく超える。

### 設計判断

- **隠す責任はサーバに置く。** `predict_service.backtest` は `include_holdout=True`
  のときしか封印側を返さない。`by_condition` も `roi_stats` も調整側だけで集計する
  — **返さなければ UI から漏れようがない**
- **開封は記録して取り消せない。** 一度見たら、その数字に合わせて選び直せてしまう。
  `holdout_revealed = {version, at}` を残し、以降ずっと「v3 で開封済み」と出す
- **どちらも良し悪しを言わない。** 「この数字を信じてよいか」の材料だけを出す

### 検証

同じ設定を3世代に分けて作ったときの調整側 ◎的中率 (実測):

```
v1 (1項目)  12.1%
v2 (2項目)  19.6%
v3 (3項目)  19.1%     ← 選ぶほど上がる形
封印側      18.7%     (基準は 調整側 32.6% → 封印側 32.8% で安定)
```

基準 (1番人気AI) が両側でほぼ同じなのは、2つの期間が比較可能であることの確認になる。

### 回帰テスト

`tests/dom_render.js` に `--backtest` モードを追加し、成績カードも実描画する。
開封後の表示で `h.your_ai.your_ai` を読んでいて**両方とも「—」**になっていた欠陥を、
このモードを足した直後に検出した (バグを戻すと落ちることを確認済み)。
