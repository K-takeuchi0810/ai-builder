1. **STEP2 の集計対象を9項目に確定 → 基底列 396**(v0.2 は 8項目/352列で暫定)。

7. リポジトリを ai-builder に確定(新規 maibuilder は作らず既存資産を流用)。

## 1. コンセプトと位置づけ

参加者が重視する項目(パラメータ)を選んで「マイAI」を組み立て、
その印の**的中率と納得感を楽しむ**ツール。

### 前提となる事実(設計の出発点)

- F3-EDGE-001 により、特徴量選択×線形重みの空間には単勝市場を上回る
  out-of-sample エッジが存在しないことが確定している。
- **v0.3 追試**: セグメント別(条件別)の重み探索も実施し、同じ結論を得た。
  - 全体重み: 35,036 候補 → OOS で人気ベースライン(ROI 0.776)を安定的に上回る設定は 0
  - 条件別重み: **119,069 候補**(全8粒度・3目的関数) + **63,525 候補**
    (月/季節粒度を追加・疎重み・信頼区間ベース採用) → **採用 0**
  - 特に**勝率・複勝率(低分散指標)では全粒度・全条件で採用ゼロ**。
    回収率で一時的に浮上した3件は、◎の勝率が 2.6〜8.0%(人気は33〜35%)の
    「大穴くじ」で、信頼区間を見れば再現しないことが確認された。
- したがって本プロダクトは**回収率商品ではない**。netkeiba AIビルダーと同じく
  エンゲージメント商品として設計する。
- 線形モデルの「エッジがない」という弱点は、「寄与が weight × feature で
  完全に分解できる」という説明可能性の強みに反転する。本プロダクトの核は
  この説明可能性である。

### DO / DON'T(位置づけ)

- DO: 「あなたのAIの◎単勝的中率は 28.4%(1番人気ベースライン: 32.1%)」のように
  事実ベースの成績を示す。実測の1番人気ベースラインは**単勝31.2〜32.9% / 複勝61.8〜63.0%**。
- DO: 印の根拠(どの特徴量が何点寄与したか)を常に表示可能にする。
- DO: **欠損とカバレッジを表示する**(§4.4)。隠さないことが誠実さの演出になる。
- DON'T: 「儲かる」「回収率100%超え」を暗示する文言・演出を一切入れない。
- DON'T: 回収率をメイン指標として表示しない(§2参照)。
- DON'T: 「賞金総額」と書かない。**「獲得本賞金」**と書く(§2.3)。

## 2. 表示指標の設計(誠実な指標セット)

### 2.1 メイン指標

| 指標 | 定義 | 表示例 |
|---|---|---|
| ◎単勝的中率 | ◎が1着になった割合 | 28.4% |
| ◎複勝率 | ◎が3着以内に入った割合 | 61.2% |
| 印内的中率 | 勝ち馬が印5頭(◎○▲△×)に含まれた割合 | 78.9% |
| 順位相関 | 印順位と着順の Spearman 相関(レース平均) | 0.42 |

### 2.2 ベースライン比較(常設)

- 「1番人気AI」(単勝人気順に印を打つだけのAI)を常時併記する。
- ユーザーAIが人気と違う◎を打って的中したレースを
  「人気を出し抜いた的中」としてハイライトする(演出の中心)。

### 2.3 賞金の呼称(v0.3 で固定)

賞金は **「獲得本賞金」** と表記する。付加賞・国際褒賞金は**含まない**。
根拠: ジャパンカップ2025 の勝ち馬には褒賞金 300 万米ドル(約4億6500万円)が別途あるが、
索引値はきっちり 500,000,000 円であり、合算額ではない(§4.3 / 証跡
`docs/evidence/20260726_prize_offset_external_check.md`)。
「賞金総額」「獲得賞金(付加賞込み)」と書くと参加者に誤解を与える。

### 2.4 回収率の扱いと**表示期間の分離**(v0.3 追加)

- 回収率はメイン画面には表示しない。詳細画面でのみ「参考値」として表示可。
  その場合は「単勝市場の控除率は約20%であり、長期的な回収率は設定によらず
  概ねその水準に収束します」の固定注記を必ず添える。
- **表示期間の分離**: プリセット重みの学習にコーナー・賞金系を含めると学習データが
  実質 2025 年以降に寄る。バックテスト再生の既定期間にも 2025 年が入ると、
  参加者に見せる的中率が「重みの学習に使ったデータ上の成績」になり僅かに盛られる。
  よって設定で分離する:

  | 用途 | 期間 | 設定キー |
  |---|---|---|
  | プリセット重みの学習 | 2021-01-01 〜 **2025-06-30** | `PRESET_TRAIN_FROM/TO` |
  | バックテスト再生の既定表示 | **2025-07-01** 以降 | `DISPLAY_BACKTEST_FROM` |

  `fit_presets()` の出力に両方を記録し、後から「どの期間で学習した重みの成績か」を
  追跡できるようにする。

## 3. 楽しさの3本柱

### 3.1 納得感(説明可能性)

- 各馬のスコア = Σ(weight_i × z_i) を寄与順に分解表示。
- 「この馬が◎の理由: タイム指数(同距離・直近3走平均) +2.1、
  最終コーナーからの着順上昇 +1.4、…」の形式。
- 線形モデルなので近似や SHAP は不要。厳密値をそのまま出せる。
- **実装済**: `model.score_race_detailed()` が
  `{key,label,weight,z,contribution,available}` を寄与の絶対値降順で返す。
- **欠損は隠さない**: 値が無い列は `available=false, contribution=0.0` として明示し、
  「この馬はコーナーデータが2走分のみ」のようにカバレッジを併記する(§4.4)。
- 賞金の寄与は「**獲得本賞金**」と表記(§2.3)。

### 3.2 成長感(マイAIの育成)

- ユーザー設定(config)はバージョン管理し、設定変更ごとに
  「マイAI v1 → v2」として成績を別トラッキング。
- 週次・月次の的中率推移グラフ。
- バックテスト再生(§7)で過去期間の成績を即時確認できる。

### 3.3 ライブ感(当日運用)

- 出走表確定時に暫定印を生成。
- 馬体重発表(発走約50分前)をトリガーに、馬体重系の列だけ差分更新し
  印を再計算。「馬体重発表で ▲→◎ に昇格!」の通知演出。
- 馬体重/馬体重変化を選択した設定では、発表前は「分析待ち」表示
  (netkeiba と同じ制約をそのまま踏襲)。

## 4. パラメータ設計

### 4.1 STEP1: 単項目特徴量(当該レースの属性)

騎手 / 枠番 / 出走間隔 / 出走頭数 / 斤量 / 血統 / 距離 / 芝・ダート /
天気 / 馬場状態 / 脚質 / 馬体重 / 馬体重変化 など。

- 実装は `builder/model.py` の特徴量レジストリ(現在 **57 特徴量**、うち可変集計 15)。
  keiba-yosou `compute_features` 由来の列を curate して公開する
  (全公開はしない。UIの認知負荷を優先)。
- 馬名の文字数・画数・誕生月などのネタ系項目は「おまけ枠」として
  明示的に区別して提供してよい(エンゲージメント商品なので排除しない)。
  ※ 誕生月・画数は現 DB に無いため実装時に要データ調達。

### 4.2 STEP2: 条件付き集計特徴量(過去走の平均) — **9項目 × 4 × 11 = 396 基底列**

v0.2 の「8項目/352列」は暫定だった。実 DB 検証で6項目が欠損していることが判明し
(証跡 `docs/evidence/20260726_maibuilder_step2_feasibility.md`)、
すべて復元・導出で補完した。**9項目すべて利用可能**。

| # | 集計対象 | 実装キー | 取得方法 |
|---|---|---|---|
| 1 | 着順 | `agg_avg_finish` | DB カラム |
| 2 | 着差 | `agg_margin` | **導出**(勝ち馬との走破タイム差) |
| 3 | タイム指数 | `agg_time_index` | **導出**(`finish_time/distance×100`、距離正規化) |
| 4 | 獲得本賞金 | `agg_prize` | **生 SE レコードから復元**(§4.3) |
| 5 | 第1コーナー着順 | `agg_corner_first` | **生 RA レコードから復元**(§4.3) |
| 6 | 最終コーナー着順 | `agg_corner_last` | 同上 |
| 7 | 第1→最終コーナーの着順上昇 | `agg_gain_first_to_last` | 同上 |
| 8 | 第1コーナーからの着順上昇 | `agg_gain_first_to_finish` | 同上 + 着順 |
| 9 | 最終コーナーからの着順上昇 | `agg_gain_last_to_finish` | 同上 + 着順 |

- 一致条件(4): 全レース `[]` / 距離が同じ `["distance"]` / 競馬場が同じ `["track"]` /
  芝ダート別 `["surface"]`
- 期間(11): 全レース `None` / 直近1〜10 `1..10`
- **9 × 4 × 11 = 396 基底列**(v0.2 の 352 から確定値に更新)
- 追加で提供可能(設計書外だが実装済): 勝率・複勝率・平均上がり3F・平均人気・
  上がり3F順位・上がり3F順位率

#### 複数選択の合成規則(v0.2 から不変)

- ユーザーが複数セルを選択した場合、**基底列の単純平均**で合成する。
- これにより事前計算は 396 列で固定され、組み合わせ爆発しない。

### 4.3 生 JV-Data からの復元(v0.3 追加) と **カバー範囲**

keiba.db に無いデータは、生 JV-Data を **read-only** で読んで ai-builder 側の索引に
保存する。**keiba.db には一切書き込まない**(不変条件)。

| 索引 | 実装 | 内容 | 検証 |
|---|---|---|---|
| コーナー通過順位 | `builder/corner.py` | RA レコードのコーナー情報(72B×4、`コーナー番号+周回+通過順位`) | **4,235 レースで馬番整合100%**、最終コーナー順位 vs 着順 **r=0.462** |
| 獲得本賞金 | `builder/prize.py` | SE レコード 1-based **366**、8桁、単位百円 | **JRA 5着ルール**(6着以降 非ゼロ率0.0%)、比率 100:40:26:15:10 一致、**公表額と一致** |

**なぜ keiba.db の該当カラムが使えないか**: `horse_races.corner_order_*` は
バイトオフセットが未検証のため安全側に倒して全ゼロ化されている(2021-2025 有効率 0.0%)。
賞金はカラム自体が存在しない。

⚠️ **カバー範囲の制約(重要)**: 生ファイル(RASW/SESW)は **2025-2026 年のみ**。
したがってコーナー系5項目と賞金は、**直近N走が 2024 年に食い込む馬で部分欠損する**。
これは長期バックテストだけの問題ではなく、**当日予想でも普通に発生する**。
→ §4.4 の欠損ポリシーで扱う。

### 4.4 欠損ポリシー(v0.3 で確定・最重要)

単一実装: `builder/normalize.py`。詳細は `docs/MISSING_DATA_POLICY.md`。

1. **列のレース内カバレッジゲート**: 値を持つ馬が **4 頭以上 かつ 出走頭数の 50% 以上**
   でなければ、その列は**そのレースで一切使わない**(誰の寄与にもしない)。
   理由: 2 頭だけの平均・標準偏差から作った z は無意味で、その 2 頭が印を独占する。
   分散ゼロの列も不使用。
2. **使用列で値が無い馬 → 寄与 0(中立)**。寄与分解に `available=false` と明示。
   **再正規化(持っている列だけで割り増す)は採用しない** — 実績の薄い馬のわずかな情報が
   増幅され、データが少ない馬が静かに有利になるため。
3. **カバレッジを返して UI で見せる**: 馬ごとに `{n_used, n_with_value}` を返し、
   「この馬はコーナーデータが2走分のみ」と表示する。欠損を誠実さに変える。

適用範囲(単一実装を共有):

| 経路 | 用途 |
|---|---|
| `model.score_race_detailed()` | 印生成・寄与分解(`/api/predict`) |
| `matrix.prepare_races()` | 事前正規化(純Python) |
| `vsearch.prepare_numpy()` | 事前正規化(numpy) |
| `presets.fit_presets()` | **プリセット重みの学習**(§5.2) |

4 経路の一致はパリティテストが担保する。

## 5. アーキテクチャ

```
[バッチ層(日次)]
  出走表確定 → matrix_daily.py            ← ★次の実装
    - 当日全レース分の396基底列 + STEP1列を PIT ゲート付きで計算
    - Parquet/JSON キャッシュ(既存 matrix.py の日次版、月次チェックポイント方式を流用)
    - **ゲート事前検査**: presets.gate_check() で「全列がゲート通過するか」を確認(§5.3)
  馬体重発表 → weight_update.py           ← ★次の実装
    - 馬体重系列のみ差分更新 → 該当設定の印を再計算・通知

[オンライン層(即時)]
  設定JSON → 列選択 → z-score正規化(欠損ポリシー) → プリセット重み内積
           → レース内順位 → 印
  応答目標: 100ms 以内(実測: 265,000行×167列の内積で約20ms → 1レースなら余裕)

[説明層]
  スコアの寄与分解(weight × z を絶対値降順)+ カバレッジをレスポンスに同梱
```

### 5.1 スコアリング方式

- v0.3 は **方式B(プリセット重み)**: 選択された列に対し、事前に学習した
  条件付きロジット係数を適用する。学習ジョブが不要なため完全リアルタイム。
- 方式A(ユーザー設定ごとの軽量オンデマンド学習)は将来拡張。

> **⚠ 方式B の構造的な制約 (2026-07-26 実測で判明)**
>
> 425列を**同時**に学習した係数は「425列すべてを使うとき」の最適解であり、
> 参加者が選ぶ数項目の部分集合では尺度が合わない。実測では
> `人気(市場)` が全重み絶対値の 23.8% を取り、他列が残差しか受け取らないため、
> 人気を選ばない設定では**一様分布より悪くなる列すらある**。
>
> 対策として `presets.fit_per_column()` (列別=単独学習) を実装した。どちらを
> 本番にするかは製品判断として未決。両ファイルを保持し、
> `python -m builder.api --weights <path>` で同一UIで比較できる。
>
> 数値と判断材料: `docs/evidence/20260726_FINDINGS_preset_weights.md`

### 5.2 プリセット重みの学習 — **ゲート委譲方式**(v0.3 で変更)

実装: `builder/presets.py`。

**カレンダーで学習窓を切らない。** 素朴には「コーナー・賞金系の係数がゼロに潰れないよう
学習窓を列ごとにカレンダーで制限する」ことを考えるが、§4.4 のゲートを**学習経路にも
通せば不要になる**:

> ゲートを通らない列はそのレースで z が生成されない → 勾配に寄与しない
> → 2021 年のレースではコーナー列が単に不使用になるだけで、
>   係数は「充填が閾値を満たすレース」からのみ学習される。

窓の管理をカレンダーからゲートに委譲する形。境界の恣意性が消え、
train-serve のゲート挙動も定義上一致する。

- **学習**: conditional logit(レース内 softmax で勝ち馬の確率を最大化、L2 正則化、
  勾配上昇)。線形なので寄与が weight × z に厳密分解でき §3.1 を満たす。
- **train-serve 一貫性(最重要)**: 学習は `matrix.prepare_races()` 経由 =
  サービングと**同一の `normalize.race_z()` 実装**を通る。
  テストで固定(`tests/test_presets.py`):
  - 学習経路が実際に `normalize.race_z` を呼ぶこと
  - 同一レースで「学習側が使う列」=「サービング側が使う列」であること
- **列別の有効サンプル数レポート**: カレンダー充填率の代わりに
  **ゲート通過レース数**を列ごとに集計。`MIN_RACES_PER_COLUMN`(既定 **500**)未満の列は
  `low_sample_columns` として警告。
  → 「参加者が賞金を選んだのに印が動かない」の検知はこれで足りる。
  実証: 賞金列を10頭中2頭だけ充填すると通過0・警告あり・**重みは厳密に 0.0**。

### 5.3 デモ当日の事前検査(v0.3 追加)

当日朝のバッチに `presets.gate_check()` を入れ、**本日の全レースで全列がゲートを
通過するか**を確認する。コーナー・賞金は 2025-2026 データで直近走が埋まるため通常は
通るが、通らないレースがあれば進行台本側で回避する。

## 6. スコアリングと印の割当(v0.2 から不変)

1. 選択列を抽出し、レース内で z-score 正規化(頭数差の影響を除去)。**欠損ポリシー適用**。
2. プリセット重みとの内積でスコア算出。
3. スコア降順に ◎ ○ ▲ △ × を割当(6頭目以降は無印)。
4. 自信度演出: 1位と2位のスコアギャップを3段階表示
   (「鉄板級」「有力」「混戦」)。閾値は学習期間の分位点で事前決定。
   **ギャップは生の差ではなく、レース内スコアの標準偏差で割った尺度不変な差**
   (`presets.normalized_gap`)。生の差は選んだ項目数と重みの大きさに比例するため、
   425列で決めた閾値を参加者の数項目の設定に当てるとラベルが機能しない
   (実測: 人気を選ばない設定で「混戦」100%)。
   → 詳細と実測値: `docs/evidence/20260726_FINDINGS_preset_weights.md` §3

5. **学習サンプルが薄い項目は開示する**。コーナー系はゲート通過レース数の中央値が
   53件、賞金系が143件しかない (生 JV-Data の保存範囲が短い)。学習窓を後ろに
   伸ばして件数を稼ぐことはせず、寄与の行と警告カードに学習レース数を明示する。

## 7. バックテスト再生

- ユーザー設定で過去期間の印を一括生成し、§2 の指標を即時表示する。
  キャッシュ行列があるため数秒で完了。
- **既定表示期間は `DISPLAY_BACKTEST_FROM`(2025-07-01)以降**
  = プリセット重みの学習に使っていない期間(§2.4)。
- 固定注記: 「過去の的中率は将来の成績を保証しません」。
- 期間はプリセット(直近3ヶ月 / 半年 / 1年)から選択。任意期間指定は将来。

## 8. API 設計(最小)

```
GET  /api/races/today
     → 当日レース一覧と分析可否ステータス(馬体重待ち / ゲート未通過列)

POST /api/predict
     body: { race_id, config }
     → { marks, scores, contributions, coverage, columns, confidence }
       contributions: [{key,label,weight,z,contribution,available}, ...絶対値降順]
       coverage:      {horse: {n_used, n_with_value}}
       columns:       [{key,label,weight,decision,n_with_value}]   # 列の採否と理由

POST /api/backtest
     body: { config, period }          # period 既定 = DISPLAY_BACKTEST_FROM 以降
     → { hit_rate_win, hit_rate_show, hit_rate_top5, rank_corr, baseline, period }

POST /api/configs                     (設定の保存・バージョン管理)
GET  /api/configs/{id}/history        (マイAIの成績推移)
```

- config スキーマ: STEP1選択リスト + STEP2選択セル(項目×条件×期間)のリスト。
- サーバ側で config を正規化ハッシュ化し、同一設定の成績を集約可能にする。
- **全スコアレスポンスに寄与分解とカバレッジを含める**(説明可能性が本体)。

## 9. データ規律(PIT) — v0.3 でテスト固定

- 発走前に確定している情報のみ使用。
- 馬体重・馬体重変化は発表タイムスタンプ以降のみ有効。
- **過去走の取得は対象レース日より厳密に前(`<`)**。
  keiba-yosou `horse_past_runs` が `(race_year||race_month_day) < ?` で実装されており、
  対象レース自身と**同日の全レース**が除外されることを確認済み。
- **テストで固定**(`tests/test_pit.py`、4件): 索引に対象レースのコーナー順位・賞金が
  存在していても過去走集計に現れないことを検証。将来 `<=` に緩めばテストが落ちる。
  v5 の leg_code リーク事故と同型のリスクを構造的に塞ぐ。
- レース確定後の変数は基底列に含めない。

## 10. Claude Code 向け DO / DON'T

- DO: 基底列は **396 列**で固定し、ユーザー選択は必ず基底列の線形結合で表現する。
- DO: すべてのスコアレスポンスに**寄与分解とカバレッジ**を含める。
- DO: 印生成・バックテスト・**プリセット重み学習**の全経路で
  `normalize.py` の欠損ポリシーと PIT ゲートを通す。
- DO: 生 JV-Data は read-only。復元データは ai-builder 側の索引に保存する。
- DON'T: ユーザー設定ごとに `compute_features` を再実行しない(キャッシュ必須)。
- DON'T: **keiba.db / keiba-yosou を変更しない**。
- DON'T: 回収率をメイン指標にする実装・文言を書かない。
- DON'T: 探索的な重み最適化を追加しない(F3-EDGE-001 と v0.3 追試で棄却済みの空間)。
- DON'T: 学習窓をカレンダーで切らない(ゲートに委譲する。§5.2)。
- DON'T: 「賞金総額」と書かない(「獲得本賞金」。§2.3)。

## 12. 10月お披露目デモ要件(競馬場・接待)

### 体験の骨格

1. 参加者がスマホ/タブレットで2〜3分パラメータを選び、マイAIに名前を付ける。
2. 次レースの印を生成し、一緒に観戦して結果と照合する。
3. 数レース繰り返し、当日リーダーボード(◎的中数、人気を出し抜いた回数)で競う。

### デモの山場(UIリソース集中投下先)

- 寄与分解の平易表示: 「なぜこのAIは7番を◎にしたか」を非技術者向けの
  一文で表示(例: 「同じ距離での直近3走のタイム指数が最も高いため」)。
- 馬体重発表のライブ更新: 発走約50分前、印の変動を通知演出付きで表示。
- **カバレッジ表示**: 「この馬はコーナーデータが2走分のみ」— 欠損を誠実に見せる(§4.4)。

### 呼称ルール(デモ・アプリ内共通)

- 個人名・役職名は画面・資料・進行台本のいずれにも使用しない。
- AI名は参加者が自由入力(デフォルト「参加者AI 1」等)。入力を強制しない。

### 信頼性要件(接待デモ特有)

- 当日朝に全レースの特徴量行列をローカルキャッシュし、通信断でも
  印生成・寄与分解・リーダーボードが動作するオフライン耐性を持つこと。
- **当日朝のゲート事前検査**(§5.3)を実施し、ゲート未通過列があるレースを把握する。
- 当日データフィード(馬体重・オッズ)は取得失敗時に「暫定印のまま」へ
  グレースフルデグレードし、エラー画面を参加者に見せない。
- 9月の実開催日に本番同一構成でリハーサルを1回実施する。

### 逆算スケジュール

- 8月: `maib_step2_specs`(396列) + matrix_daily + API + プリセット重み確定
- 9月前半: モバイルファーストUI(Claude Design → MudBlazor)
- 9月後半: 実開催リハーサル
- 10月: 本番
