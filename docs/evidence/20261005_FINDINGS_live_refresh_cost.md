# ライブ更新がまだ 97 GB/日 読んでいる — 計測と、次の開催日への仕込み (2026-10-05)

`20260818_FINDINGS_live_refresh_io.md` で払戻の読み直しを 142 MB/サイクル → 0 にしたが、
**本番の常駐プロセスは 97.75 GB/日 読んでいる**。残りの出どころを特定するところまで進めた。

---

## 1. 本番の実測

```
PID 4648   稼働 5.98 日   累計読み取り 584.43 GB   = 97.75 GB/日   CPU 1,576 秒
```

修正前は約 490 GB/日 だったので 8 割は落ちている。ただし 0 ではない。

### 開催が無い日は 0

月曜 (開催なし) に 10 秒刻みで 50 秒サンプリング:

```
0.00 MB / 0.00 MB / 0.00 MB / 0.00 MB / 0.00 MB   → 0.0 GB/日 相当
```

**払戻の修正は効いている。** 残りは開催日に集中している。

## 2. 1サイクルの中身 (20261004 · 24レース)

`refresh_live` を実データで計測:

| 周 | 所要 | 生ファイル読み取り |
|---|---|---|
| 1周目 | **275.3 秒** | 0.02 MB |
| 2周目 | **0.2 秒** | 0.00 MB |
| 3周目 | **0.1 秒** | 0.00 MB |

**生ファイルはもう読んでいない。** 時間は別のところで使われている。

### プロファイル (1周目)

```
267.7s  refresh_live
266.5s   └ _compute_features (361回)
151.2s      └ sqlite3.execute (9,830回)
114.8s      └ fetchall (8,673回)
133.8s   内訳: _track_recent_stats
114.3s   内訳: bloodline_stats
  0.7s   払戻の読み取り (修正済み)
```

**当日特徴量の再計算が 99.6%。** 1レースあたり 8〜12 秒、約 400 本の DB 問い合わせ。
19.75 GB の `keiba.db` を引くので、これが 97 GB/日 の正体と考えられる。

## 3. なぜ 1周目だけ重いのか

`refresh_live` は指紋で守られている:

```python
next_feature_context = _feature_context(live_seg, live_horses)
recompute_live_features = recompute_features and (
    cached.get("live_feature_context") != next_feature_context)
```

指紋の中身は **馬場・競馬場・芝ダート・距離・(馬番, 騎手, 負担重量)** だけ。
オッズや馬体重は入っていないので、通常は変わらない。

1周目が重いのは、**ディスクのキャッシュファイルから読み直した直後**で、
保存されていた指紋と現在の DB の値が食い違うため。2周目以降は一致して 0.2 秒。

**設計は妥当。** 問題は「開催日に指紋が何回変わっているか」が分からないこと。

## 4. ここで止めた理由

97 GB/日 を説明するには、開催日に**毎サイクル近く**再計算が走っている必要がある。
しかし月曜に開催日の DB 変化は再現できない。

**推測で直すと、効いたかどうかも分からない。**
`_feature_context` からどれかの項目を外せば回数は減るが、
外した項目が本当に特徴量に影響しないという根拠がない
(`condition` は馬場適性の特徴量に効く)。

## 5. 仕込んだ計測

再計算が走るたびに、**理由と所要**をログに残す。

```
当日特徴量を再計算: race=2026100408040205 頭数=12 理由=condition:良→稍重
当日特徴量を再計算: race=2026100408040205 完了 8.2秒
```

- 指紋の中身を `live_feature_parts` として保存し、次回との差分を項目名で出す
- 騎手欄は全件ではなく「何頭ぶん変わったか」(ログを膨らませない)
- 前回の記録が無いときは `(前回の記録なし)` と書く — **差分を捏造しない**

### 次の開催日 (10/10 以降) に見ること

```
powershell -Command "Select-String -Path out\logs\service.log -Pattern '当日特徴量を再計算' | Select-Object -Last 60"
```

- **回数**: 1レースあたり1日に何回か。数回なら妥当、数十回なら異常
- **理由**: `condition` が繰り返し往復しているなら、指紋の取り方に問題がある
- **所要の合計**: 回数 × 10秒 が稼働時間に対してどれくらいか

## 6. テストで固定したこと

- 同じ入力なら指紋が変わらない (馬の並び順にも依存しない)
- 馬場・騎手・負担重量が変われば指紋が変わる
- **オッズ・馬体重では変わらない** — 入れると毎周回ってしまう
- 差分は項目名で返し、記録が無ければ `(前回の記録なし)` と言う

## 7. まだ直していないこと

**97 GB/日 の内訳は未確定。** 開催日のログが出るまで、原因を1つに絞れない。

考えられる経路 (いずれも未検証):

- 馬場状態が開催中に何度も変わる → そのたびに同じ競馬場の全レースを再計算
- 指紋に入っている値が DB 側で揺れている (型や空文字の違いで往復する)
- 朝の `build_daily` (`--build: true`) — 1日1回なので主因にはなりにくい
- `handle_betslip` → `odds._raw_o1` が 16,925 ファイルの `0B30` を毎回 glob する
  (レースキーで絞っているので読み取りは小さいが、走査は毎回)
