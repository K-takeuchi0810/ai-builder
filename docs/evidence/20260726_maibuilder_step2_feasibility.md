設計書の「集計対象9項目 × 一致条件4種 × 期間11種 = 352基底列」を、実 DB (keiba.db) に
対して検証した。**9項目のうち6項目はデータが存在せず、現仕様のままでは実装不能。**

## 提案: STEP2 の集計対象を実在データで再定義

コーナー系5項目を落とし、`finish_time`/`final_3f` ベースの導出項目に置き換える:

1. 着順 (confirmed_order)
2. 着差 (finish_time の race 内 1着差) ← 導出
3. タイム指数 (距離正規化タイム, best_time_per_100m 相当) ← 導出
4. 上がり3F (final_3f)
5. 上がり3F 順位 (race 内順位) ← 導出
6. 人気 (win_popularity)

**6項目 × 一致条件4 × 期間11 = 264 基底列**。設計書のアーキテクチャ(基底列固定+
線形結合)はそのまま維持でき、組み合わせ爆発もしない。

※ コーナー系を復活させたい場合は、JV-Data の該当 dataspec を ingest する
   データ層の作業が先に必要 (keiba-pipeline 側の課題)。10月デモまでの逆算では
   8月に判明していないと危険。

## 設計書の他項目について (実測との照合)

- **§2 ベースライン「1番人気AI」**: 実測と整合。1番人気の単勝的中率は
  **31.2〜32.9%**、複勝率 **61.8〜63.0%** (2024/2025実測)。設計書の例
  (32.1% / 61.2%) は妥当。
- **§5 応答目標100ms**: 妥当。事前正規化済み行列の内積は 265,000行×167列でも
  約20ms (実測)。1レース分なら余裕。
- **§1 前提 (F3-EDGE-001)**: 追加検証でさらに裏付けられた。単勝バリューベット
  35,036候補に加え、**セグメント別探索を 119,069候補 + 63,525候補**実施し、
  月粒度・季節粒度を含む全14粒度・3目的関数で**採用ゼロ**。§10 の
  「探索的な重み最適化を追加しない」は妥当。
- **§5「既存 matrix.py の月次チェックポイント方式を流用」**: ai-builder に実装済み
  (`builder/matrix.py`)。日次版への転用可能。
